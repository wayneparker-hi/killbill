# 产品目标与独立验收证据补齐

日期：2026-11-05。状态：执行中；[同机双 WAR 阶段](dual-war-validation.md)先交付部署证据，其余验收项目保持待执行。

## Why

依据 [系统目标](../../spec/killbill.md)，本 fork 保留 Kill Bill 业务语义，以 LPR 替换 OSGi，并简化插件开发和运维。下一阶段需要将资金正确性、升级期间的业务连续性和维护收益转化为可复现证据。

本提案记录证据缺口，不将“尚无充分证据”等同于“功能缺失”。现有测试、归档记录和 CI 配置作为起点；历史通过不代表当前提交已复跑，配置 CI 不代表远端执行成功。

## 方法与依赖

- PA-01 使用独立案例预期或 Python Decimal 参考计算，不能复制生产算法后宣称独立；金额预期不得从被测 API 结果反推。
- PA-02 先用独立进程、持久账本的受控网关模拟器复现故障，再用选定网关沙箱获取外部证据。模拟器结果只证明受控协议场景，沙箱结果不等于真实清算证明。接入凭据缺失时标记待外部条件，不算通过。
- PA-03 先明确在途调用契约及停止截止时间，不预设“无限排空”；若需新增调用租约/延迟关闭，必须先更新对应 spec 并以失败证据支撑设计。
- PA-04 与 PA-01 可先行；PA-02 的网关账本供 PA-03 复用，PA-05 复用升级夹具。PA-06/07 可独立推进。
- P1 的负载、时长、容量、责任人及响应阈值在执行前确定并记录；本规划不虚构生产流量或收益数字。

## Impact 与范围边界

初始规划仅新增文档及索引。执行阶段按当前验收目标更新 `spec/` 与证据映射；同机双 WAR 阶段只修改验收工具、夹具和文档，不修改生产 Java/POM、公共 API 或装配绑定。

执行每项前核对当前源码与已有结果，将验收契约写入相关 capability spec（并映射可执行测试）；涉及行为变化时先提交 delta 与方案，再修改实现。发现不符时只修复有证据的缺陷，沿用 Core/Platform 不依赖具体插件等架构约束。

MySQL 支持发布前必须验证 MySQL；多主机/共享存储部署前必须验证实际锁、原子发布、节点故障及网络影响；启用 Redis 业务能力前验证该能力；生产容量与备份恢复在选定拓扑后验收。未验证的环境不得宣传为已支持验收。

插件市场、恶意代码沙箱、自动依赖解析、进程外插件生产化继续保持当前系统规格的范围边界。历史基线只在隔离环境运行，不把 OSGi/Felix 引回当前项目。

完成证据包含提交号、JDK/DB/工具版本、制品摘要、输入与独立预期来源、命令/退出码、测试数/失败/跳过及负例结果。报告中区分本地测试、远端 CI、网关沙箱和生产观测；避免将凭据及未脱敏业务数据加入仓库或公开 CI 制品。
