## 结果与边界

同机独立 JVM 中暂停整个 A，待租约过期且 B 经生产 reaper 接管，再恢复 A。迟到成功 ACK 与异常重试均未改写 B 的新物理记录，B 可完成，最终无 active 消息，UUID 夹具业务效果一份。

迟到成功会追加旧 owner 的 PROCESSED，历史按尝试解释。本轮未发现需要生产修复的缺陷；没有修改生产 Java、POM、公共 API 或装配，也未增加锁、选主或 fencing。

95 reactor / 22 ABI、14 项 PostgreSQL、真实 WAR 支付与重启、307 项相关回归、8 项 Python 守卫及 7 项单变量变异检查通过。6 个完整验收库及所有变异库均已精确删除。

夹具业务效果在暂停前提交，仅覆盖 A 在 B 仍在途时返回的两种结果；不证明所有 SQL 交错、外部支付幂等或 exactly-once。未覆盖仅卡 handler、双真实 WAR、多机、网络分区或远端 Linux CI。Redis 仅 PING，七项静态门禁按规约跳过。

# 过期租约下旧 worker 恢复验证

## Why

双节点验证只覆盖终止旧节点后的接管。旧 JVM 暂停超过租约、B 重放后 A 恢复执行尚无实测，不能据此判断是否需要生产防护。

## What Changes

- 暂停本次 A 子 JVM（SIGSTOP），由正在运行的 B 使用生产 reaper 接管同 UUID，再恢复 A（SIGCONT）。
- 在 B 仍在 handler 中时验证 A 的迟到成功 ACK、迟到异常重试；核对新物理记录、owner、错误计数和业务结果。
- 同时检查两个进程实际存活/暂停状态、过期时间、跨节点投递及最终排空，纳入独立 PostgreSQL 验收。
- 先取得可复现证据；若符合至少一次及历史尝试语义，记录边界，只有确认丢消息/破坏新记录等缺陷才最小修复。

## Impact

无预设 fencing、选主、锁或新产品能力；不覆盖双 WAR、多机、网络分区和支付外部副作用。测试唯一键只验证夹具业务幂等。
